Software-inventory difference between the `dkfz_minimal` 1.1.0 and 1.1.0-testing images, for review.
RPM and PyPI packages are derived from the Trivy CycloneDX SBOMs (`dkfz_minimal-1.1.0-testing.cyclonedx`).
The CPAN modules are listed separately because Trivy does not inventory Perl dependencies,
so they do not appear in the SBOM; the complete inventory is in `cpan-modules.txt`.

NOTE: `1.1.0-testing` is a *test-only* image (`dkfz_minimal:1.1.0` plus test
frameworks and code-quality tooling); it is not a production runtime, so the
added packages never affect a real workflow environment.

== Interaction with `module load`ed interpreters

The added packages do not interfere with the software the workflows activate via
`module load` (the frozen `PERL_VERSION` / Python installations mounted into the
container). This was verified against the built image; for Perl specifically:

* *The modules live in the system Perl's `site_perl` only.* `cpanm` installed
  them under `/usr/local/lib64/perl5` and `/usr/local/share/perl5`, which are on
  the `@INC` of the container's *system* Perl (`/usr/bin/perl`, v5.16.3) and of
  no other interpreter.
* *`module load` selects a different `perl` with its own `@INC`.* A module-tree
  Perl has its own installation prefix (e.g. `/software/.../perl/<version>/...`)
  and therefore its own version-specific `@INC`; it does not read the system
  Perl's `/usr/local/.../perl5` `site_perl`.
* *Nothing forces the modules onto another interpreter.* `PERL5LIB` is empty in
  the image and is not set by the container's `profile.d` scripts, so no global
  search path leaks these modules into a `module load`ed Perl. This is precisely
  why they were installed into `site_perl` rather than a Carton `local/` tree
  behind a global `PERL5LIB` -- the latter *would* have been honoured by every
  Perl, including a different-versioned one (a real risk, given XS ABI
  compatibility).

Residual case: a `module load`ed Perl that is itself 5.16.3 *and* configured with
a Red-Hat-style `@INC` that includes `/usr/local/.../perl5` would additionally
see these modules. That is purely additive -- all the added modules are
pure-Perl -- and the module tree's own `@INC` entries precede the system
`site_perl`. The same reasoning applies to `pytest` and a `module load`ed
Python: it sits in the system Python 3.6 `site-packages`, `PYTHONPATH` is empty,
and a module-loaded Python of another version uses its own `site-packages`.
